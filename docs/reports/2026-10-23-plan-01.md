# Plan 1 report: server foundation

Branch `plan-01-server-foundation`, 38 commits from `3922f5d`. Every task was built test-first, reviewed on its own, and then the whole branch was reviewed on Opus. A red-team pass attacked the running code. 236 tests pass on a clean build, with 0 skipped.

## What exists now

The Spring Boot server signs users in with an email code and issues 15-minute access tokens and rotating refresh tokens. It stores the profile (income, savings, payday, personality, message times) and fixed costs. It works out the pay cycle in Indian time and answers `GET /api/v1/budget/today` with the budget, spent, left, mood and Gullak's line. The README lists every endpoint and every setting the server reads.

## Decisions waiting for you

1. **First month's budget.** Someone who signs up on 23 October with payday on the 1st would see a full month's money spread over 9 days, about ₹1,666 a day instead of about ₹483. Decided: the first cycle gets only the share for the days left. Setup asks "How much money do you have left until payday?", pre-filled with that figure. It is recorded in spec 2.1 and in test case BUD-32, and is built in Plan 2. Say so if you want it to work differently.
2. **Changing payday.** When the payday moves, the app adds a short in-between cycle, as the spec defines (BUD-18). That short cycle currently gets a full month's money. I left it as the spec says. Decide whether it should be pro-rated like the first month.
3. **Lock-out by a stranger.** Anyone who knows an email can type 10 wrong codes and block that person's sign-in for a day. The same daily cap is what makes guessing a code practically impossible, so I kept it for V1. If it turns into a support problem, the fix is codes tied to the device that asked for them.

## Decisions taken, with reasons

| Decision | Why | Cost if wrong |
|---|---|---|
| Spring Data JPA, with plain SQL only for spend totals | Your instruction; Flyway still owns the schema | none |
| Model per task: Sonnet or Haiku where the plan had the full code, Opus for sign-in, tokens, security and the core budget review | Speed and cost without risk where it matters | none; reviews caught what cheaper models missed |
| One live sign-in code per email, a lock per email, at most 10 wrong codes per email per day | Brings the yearly odds of guessing one person's code from about 73% to well under 1% | a user who mistypes 10 times waits until tomorrow |
| Client IP taken from proxy headers only when the request comes from a listed trusted proxy; production refuses to start without the list | Stops anyone faking their IP to dodge limits | must set `GULLAK_TRUSTED_PROXIES` before deploy |
| Refresh token reuse signs out every session; an expired or already-logged-out token is just refused | Catches stolen tokens without turning old tokens into a sign-out-everywhere switch | a stolen token logged out before use no longer triggers the alarm, but it is already dead |
| Daily budget rounded down to whole rupees, with the paise left in the pool | Every figure on Home adds up; the spec's ₹593, ₹577 and ₹333 still hold | up to ₹1 a day held back until the next recalculation |
| Gullak faints only when today's spend passes the budget or the pool is below zero; a ₹0 budget with nothing overspent shows nervous | That is the spec's wording; zero is "used up", not "overspent" | a mood tweak |
| The "over by" line includes the pool's shortfall | Matches the spec's "over by ₹400" example | a copy change |
| Income capped at ₹10 crore a month | The code's own comment said so; the spec is silent | raise one constant |
| Numbers with decimals or sent as text are refused in every amount field | Silently changing 1.5 to 1, or reading "100000" as a number, is a data bug | a future decimal field must opt out |
| Request bodies limited to 64 KB | Spec API-X-08; stops memory abuse on public routes | statement uploads (Plan 4) get their own limit |
| Code checks limited to 30 per email per 15 minutes | Spec 4.7 asks for a per-email limit; at 10 the existing guess-lock test broke, and guessing is already capped | none for security |
| Pay cycles can never overlap, enforced by the database | An overlap made Home fail for a user for up to a month | none |

## Red team

No Critical or High findings: no user could read or change another user's data. The team fixed four Medium issues: no size limit on requests, amounts accepted as text, a hidden character crashing the server and using up the sign-in code, and no per-email limit on code checks. They also fixed one Low: the server's monitoring paths answered "please sign in" instead of "not found". 27 more attacks were blocked and are kept as tests. Details: `docs/reports/red-team/plan-01.md`.

## Before the first production deploy

- Set `GULLAK_JWT_SECRET`, `GULLAK_OTP_PEPPER`, `GULLAK_TRUSTED_PROXIES` and the database settings (README, "Configuration").
- Production will not start until a real email sender exists (Plan 8).
